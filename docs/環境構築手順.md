## 1. Flutter SDKのインストール

### Windows

1. [Flutter SDK](https://docs.flutter.dev/get-started/install/windows) をダウンロード
2. `C:\src\flutter` などに展開(パスにスペース・日本語は禁止)
3. 環境変数`Path`に`C:\src\flutter\bin`を追加


## 7. 外部API・バックエンドについて

駅・路線データはHeartRails Express、グルメ検索はホットペッパー、観光検索はFoursquare、候補の要約はClaude APIを使う。
外部APIの呼び出しは、Firebase Functions(`functions/`)の`getCandidates`が行い、アプリからは呼ばない(APIキーをアプリに入れないため)。
履歴・お気に入り・利用回数は、Firestoreに保存する。

### 7-1. お問い合わせメール(`sendInquiry`)の設定

アプリ内の問い合わせフォームは、`sendInquiry`がResend経由で運営者のメールに送る(Issue #119)。
APIキーと受信先のメールアドレスは、リポジトリに入れず、Firebaseの Secret に登録する。

1. [Resend](https://resend.com/)のアカウントを、受信したいメールアドレスで作り、APIキーを発行する
   (独自ドメインがない間は、差出人がResendのテスト用アドレスになり、登録したアドレスにだけ届く)
2. Secretを登録する(値は、実行後の入力画面で貼る)

```bash
firebase functions:secrets:set RESEND_API_KEY --project burari-date
firebase functions:secrets:set INQUIRY_TO_EMAIL --project burari-date
```

3. デプロイする: `firebase deploy --only functions --project burari-date`

Secretが未登録のままデプロイすると、入力を求められて止まる。先に登録すること。

### 7-2. 公式サイト(`site/`)の更新と公開

公式サイト(トップ・利用規約・プライバシーポリシー)は、静的なHTMLを`site/`に置き、Firebase Hostingで公開する(Issue #139)。
Google Playの組織アカウントの「組織のウェブサイト」と、ストアに登録するプライバシーポリシーのURLに使う。

- 利用規約・プライバシーポリシーのページは、アプリの文面(`legal_texts.dart`)から作る。文面を直したら、作り直す:
  `dart run tool/build_site.dart`(アプリとサイトの文面がずれると、テストが失敗する)
- トップページ(`site/index.html`)と`site/style.css`は、手で直す
- 公開: `firebase deploy --only hosting --project burari-date`(URL: https://burari-date.web.app)
- `site/google….html`は、Search Consoleの所有権の確認用のファイル。**消さない**(消すと、Play Consoleのウェブサイトの確認が外れることがある)
- `firebase.json`の`cleanUrls`は`false`のまま変えない(trueにすると、確認用のファイルがリダイレクトされて、確認できない)
- 公開前の文面のため、検索には出さない設定(`noindex`)にしてある。公開する準備が整ったら、各HTMLの`noindex`と、`firebase.json`の`X-Robots-Tag`を外す

### 7-3. 課金(RevenueCat)の通知の受け取り(`revenueCatWebhook`)の設定

RevenueCatからの通知(Webhook)を、`revenueCatWebhook`が受け取り、購読の状態を、`users/{uid}`の
`subscriptionStatus`・`subscriptionExpiresAt`に保存する(Issue #133)。通知は、「状態が変わった」という
合図として使い、状態は、RevenueCatのREST APIで取り直す(通知は、重複・順番の前後があり得るため)。
月の回数の判断(購読中は月30回)は、この状態を見る(`functions/src/fairUse.ts`)。

アプリのRevenueCatのアプリユーザーIDには、**FirebaseのUID**を使う(#132)。

1. RevenueCatのダッシュボードで、月額プランの商品を、**`burari_date_pro`**という名前のEntitlementにつなぐ(RevenueCatのプロジェクトを作ったときに、自動で作られた名前。月額・年額・買い切りの商品が、つながっている)
   (名前を変えるときは、`functions/src/subscription.ts`の`PREMIUM_ENTITLEMENT_ID`も合わせる)
2. RevenueCatの**Secret API key**(v1のREST API用)を発行する
3. Webhookの認証用の値を、自分で決める(推測されない、長いランダムな文字列)
4. Secretを登録する(値は、実行後の入力画面で貼る。**チャットには貼らない**)

```bash
firebase functions:secrets:set REVENUECAT_API_KEY --project burari-date
firebase functions:secrets:set REVENUECAT_WEBHOOK_AUTH --project burari-date
```

5. デプロイする: `firebase deploy --only functions --project burari-date`
   (デプロイの出力に、`revenueCatWebhook`のURLが出る。Secretが未登録だと、入力を求められて止まる)
6. RevenueCatのダッシュボードの、Integrations → Webhooks で、次を設定する
   - Webhook URL: 5 のURL
   - Authorization header value: 3 で決めた値(`REVENUECAT_WEBHOOK_AUTH`と同じ)
   - 本番とサンドボックス(テスト購入)の通知を、どちらも受け取る(環境を絞るときは、2つ作る)
7. 疎通を確かめる: ダッシュボードから、テスト用の通知(TEST)を送る(`ignored`の200が返れば、認証は通っている)

**iOS(App Store)の月額プラン(1回だけ)**

Webhook・Secret・Entitlementは、Androidと共通(サーバーの変更は要らない)。アプリの側は、OSに合わせて、
APIキー(`productionRevenueCatApiKey`)と、解約の案内・購読の管理の画面(`SubscriptionStore`、
`lib/core/config/subscription_store.dart`)を切り替える。

1. App Store Connectで「有料アプリ契約」を結ぶ(銀行口座・税務の情報。済むまで、サブスクを販売できない)
2. App Store Connect → アプリ → サブスクリプションで、サブスクリプショングループと、月額の商品を作る
   (価格はAndroidと同じ月額300円。表示名・説明・審査用のスクリーンショットも入れる)
3. App Store Connect → ユーザとアクセス → 統合 → アプリ内課金で、**アプリ内課金キー**(.p8)を作る
4. RevenueCatのダッシュボードで、iOS(App Store)のアプリを追加し、Bundle ID
   `com.buraridate.burariDate`と、3 のキーを登録する
5. 2 の商品を取り込み、Entitlement `burari_date_pro`と、いまのOfferingの月額のパッケージにつなぐ
   (アプリは、Offeringの`monthly`のパッケージを買う。Androidの商品と同じパッケージに入れる)
6. 4 のアプリの公開APIキー(`appl_`で始まる)を、`lib/core/config/revenuecat.dart`の
   `kRevenueCatIosApiKey`に入れる。**空のまま審査に出さない**(購入が「設定が、まだ済んでいません」になる)
7. TestFlightのビルドで、サンドボックスのアカウントで購入・復元・解約を確かめる
   (デバッグビルドは、Test Storeのキーで擬似的に購入する)

### 7-4. Google Playにアップロードするビルドの署名(アップロード鍵)

Google Playは、デバッグ用の署名のアプリ(AAB)を受け付けない。リリースのビルドは、**アップロード鍵**で
署名する(Issue #147)。Google Playの「Playアプリ署名」を使い、Google側の鍵で、配信用に署名し直される。

- 鍵のファイル(`.jks`)は、**リポジトリの外**に置く(この環境では、`C:\Users\kinno\.burari-date-keys\upload-keystore.jks`)。
  パスワードは、`android/key.properties`に書く(`.gitignore`済み。リポジトリに入れない)
- **鍵のファイルと、パスワードは、必ずバックアップする**(パスワード管理ソフトなど)。なくすと、アプリを更新できなくなる
  (Google Playのサポートへ、アップロード鍵のリセットを申請することになる)
- `android/key.properties`がない環境(開発・stgのCIなど)では、これまでどおり、デバッグ用の署名でビルドする
- ローカルで、本番のAABを作る: `flutter build appbundle --flavor prod -t lib/main_prod.dart --release`
  (`build/app/outputs/bundle/prodRelease/app-prod-release.aab`)
- 署名の確認(公開してよい指紋): `keytool -printcert -jarfile build/app/outputs/bundle/prodRelease/app-prod-release.aab`

**本番のタグ(`v*.*.*`)のCI**で署名するには、GitHubのSecretsに、次を登録する(登録するまでは、署名しないビルドになり、
Google Playにはアップロードできない)。値は、チャットには、貼らない。

| Secret | 内容 |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | 鍵のファイルを、base64にした文字列(`base64 -w0 upload-keystore.jks`) |
| `ANDROID_KEYSTORE_PASSWORD` | `key.properties`の`storePassword`(鍵のパスワードと同じ) |
| `ANDROID_KEY_ALIAS` | `upload` |

- 注意: 本番のタグのCIは、AABを、GitHubのReleaseに、公開する(公開リポジトリでは、誰でもダウンロードできる)。
  公開前のアプリを、公開したくないときは、`deploy-prod.yml`の`Create GitHub Release`の`files`を外す

### 7-5. App Check(正規のアプリからの通信だけを通す仕組み)の設定

公開リポジトリでは、Firebaseの設定値が見えるため、第三者が匿名ログインして、サーバーの関数を直接呼べる。
費用につながる関数(`getCandidates`・`describeCandidates`・`sendInquiry`)を、**正規のアプリからの呼び出し
だけ**にするために、App Checkを使う(Issue #222)。利用者に、登録などの操作は求めない。

- アプリ側(実装済み): 起動時に有効にし、Cloud Functionsの呼び出しに、自動で証明のトークンが付く
  (`lib/data/datasources/cloud/app_check_setup.dart`)
  - **prodのリリースビルド**: Play Integrity(Google Playから入れた、正規のアプリだけが通る)
  - **dev・stg、デバッグビルド**: デバッグ用(ストア以外から入れるため)
  - iOSも同じ区分で選ぶ(本番はDeviceCheck、それ以外はデバッグ用)。iOSのDeviceCheckは、App Storeから入れたアプリで確かめる
- サーバー側: いまは**必須にしていない**(監視のみ)。トークンがなくても、動く。ログの`verifications.app`が、
  `VALID`(通った)か`MISSING`(トークンなし)か`INVALID`(不正)かで、状況を確かめられる

**Firebaseコンソールでの設定(1回だけ)**

1. 「App Check」→「アプリ」→ Androidの**prod**のアプリ(`com.buraridate.burari_date`)で、「Play Integrity」を選んで登録する
   - Google CloudコンソールのAPIで「Play Integrity API」を有効にする
   - 「プロジェクトの設定」で、そのアプリに、**Play App Signingの署名のSHA-256**を登録する(Play Consoleの「アプリの完全性」で読める)
2. dev・stgを試すときは、デバッグトークンを登録する
   - デバッグビルドでアプリを起動すると、`adb logcat`に`Enter this debug secret into the allow list in the Firebase Console`と、トークンが出る
   - 「App Check」→「アプリ」→ 該当のアプリの「︙」→「デバッグトークンを管理」で、そのトークンを登録する(端末ごと)

**必須にする手順(順番が大事)**

公開中の古い版(App Checkを入れる前の版)は、トークンを付けないため、必須にすると、**そのまま使えなくなる**。

1. App Check入りの版を、Google Playで配信する
2. 「App Check」→「APIs」(Cloud Functions)の**メトリクス**で、検証に成功したリクエストの割合を見る。古い版の利用が
   十分に減る(更新の案内、Issue #223・#224で促す)まで待つ
3. `getCandidates`・`describeCandidates`・`sendInquiry`に`enforceAppCheck: true`を付けて、デプロイする
4. 古い版で使えなくなる利用者がいるため、必要なら、先に更新の案内を出す期間を長くとる

### 7-6. ログイン(Google・Apple)の設定

アカウントの登録・ログインは、AndroidはGoogleだけ、iOSはAppleとGoogleの両方を出す
(`loginMethodsFor`、`lib/presentation/providers/account_providers.dart`)。Googleなどの外部の
ログインを出すiOSアプリは、Appleでサインインも出す必要がある(App Storeの審査ガイドライン4.8)。

**Google(iOS)**

- iOS クライアントID(`kGoogleIosClientId`、`lib/core/config/google_sign_in.dart`)は、Firebaseに登録した
  iOSアプリ(`com.buraridate.burariDate`)のもの。次で確認できる
  ```bash
  firebase apps:sdkconfig IOS 1:889357641434:ios:b58cd38ba9138f612d27e3 --project burari-date
  # CLIENT_ID / REVERSED_CLIENT_ID
  ```
- `ios/Runner/Info.plist`の`CFBundleURLTypes`に、`REVERSED_CLIENT_ID`をURLスキームとして登録している
  (ログインのあと、アプリに戻るため)。クライアントIDを変えたら、両方を揃える(テストで確かめている)

**Apple(1回だけ)**

1. Apple Developer → Identifiers → `com.buraridate.burariDate`の「Sign In with Apple」を有効にする
   (Xcodeの自動署名でも有効になる。entitlementsは`ios/Runner/Runner.entitlements`に設定済み)
2. Firebaseコンソール → Authentication → ログイン方法 → 「Apple」を有効にする
3. アカウントの削除のときに、Appleとの連携を解除(トークンを無効に)するため、同じ画面の
   「OAuth コードフローの構成」に、Apple Developerの**Team ID**・**Key ID**・**秘密鍵**(Keys で
   「Sign in with Apple」を有効にして作る`.p8`)を入れる。`.p8`はリポジトリに入れない
   - 入れていないと、Appleで登録したアカウントの削除が、「Appleとの連携を解除できなかった」で失敗する
     (審査ガイドライン5.1.1(v)のため、解除できないときは、削除に進まない)
